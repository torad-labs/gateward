From a review comment to impossible

One pass through the growth loop, with the real artifacts. This is not a tutorial reconstruction: the rule, the payloads, and the red run below are this repository's actual history — the regression that fixed case-history defect #1.

1 · The comment

A reviewer writes, for the second time this month:

This reads SharedPreferences inside the domain layer — domain must not
know Android exists. Move the Context behind an interface in data.

Twice is the threshold. This stops being a comment and becomes a rule.

2 · The rule

packs/android-architecture/rules/no-context-in-domain.yml — the whole thing. Note files: — the rule is path-scoped: it only judges files that live in a domain layer.

id: no-context-in-domain
language: kotlin
severity: error
message: >-
  Domain must not know Android exists — no Context here. Put the Android
  dependency behind an interface implemented in the data layer.
metadata:
  tier: deny
files:
  - '**/domain/**'
rule:
  kind: parameter
  has:
    kind: user_type
    has:
      kind: type_identifier
      regex: '^Context$'

3 · The rule's own tests

rule-tests/no-context-in-domain-test.yml: what must match, what must not. ast-grep test runs these standalone inside the pack.

id: no-context-in-domain
valid:
  - |
    class SettingsStore(private val prefs: PreferencesGateway) {
        fun isDark(): Boolean = prefs.readBoolean("dark")
    }
invalid:
  - |
    class SettingsStore(private val context: Context) {
        fun isDark(): Boolean =
            context.getSharedPreferences("s", 0).getBoolean("dark", false)
    }

4 · The wire — proving the gate sees it

A rule that passes its own tests can still never fire in production. So the rule gets an end-to-end payload: a real PreToolUse body, piped through the real entrypoint by e2e/run.py.

{
  "tool_name": "Write",
  "tool_input": {
    "file_path": "{{WORKSPACE}}/app/src/main/kotlin/com/example/domain/SettingsStore.kt",
    "content": "package com.example.domain\n\nimport android.content.Context\n\nclass SettingsStore(private val context: Context) { ... }"
  }
}

5 · Red

The run that justified the whole step:

FAIL  13-write-context-in-domain  expected deny, got allow

12/13 passed

The rule was green in its own tests and dead in the gate. The engine scanned projected content from a bare temp file, so the file's real path — the /domain/ segment the rule keys on — was erased before ast-grep ever saw it. Path-scoped rules could never fire on a live edit, and nothing in the existing suites could know.

6 · The fix

The scanner now mirrors the file's project-relative path under a temp directory, so rule-level files: globs see the real shape (engine/scan.py):

# Mirror the file's project-relative path under a temp dir. Rule-level
# files:/ignores: globs (e.g. **/domain/**, **/test/**) match on path
# shape; a bare temp name would erase it and those rules could never fire.
root = config.config_dir.parent.resolve()
rel = Path(path).resolve().relative_to(root)
tmp = Path(tmpdir) / rel

7 · Green

PASS  13-write-context-in-domain

13/13 passed

And the verdict the model now receives, in the same turn as its attempt:

{"hookSpecificOutput": {
  "hookEventName": "PreToolUse",
  "permissionDecision": "deny",
  "permissionDecisionReason": "[no-context-in-domain] line 5: Domain must not know
   Android exists — no Context here. Put the Android dependency behind an
   interface implemented in the data layer."
}}

The agent reads the reason, defines the interface in domain, implements it over SharedPreferences in data, and proceeds — architecture enforced mid-generation. The reviewer never writes that comment again, because the situation it corrects can no longer exist.

What breaks — skip a step and here is your failure

Skip the rule tests and the pattern encodes what you imagined, not what the parser builds. A wrong node kind matches nothing, forever, silently — a rule that is green by vacuity. The invalid case is the rule's heartbeat.
Skip the e2e payload and you get defect #1 verbatim: a rule alive in its unit tests and dead in the gate, because some engine detail — a temp path, a config resolution, an extension filter — eats it in transit. Only a payload through the real entrypoint proves the gate sees what the rule sees.
Skip the golden sweep and false positives ship. The first time the gate blocks correct code, the team stops trusting every verdict it will ever emit. Golden audits zero, always, and a rule that fires on it gets tightened, never the app.
Soften it to a warning and you have shipped documentation, not enforcement. Agents ignore warnings; humans do too, honestly. This system has no warning tier by law (T2) — a finding blocks, is autofixed, or the rule should not exist.
