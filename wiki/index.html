portable-hooks · the book · first edition

Engineering tenets, enforced at write time

An agent writes code faster than any process built to review humans can absorb. This book describes a small system that moves your architecture, conventions, and best practices out of documents a model might read and into a gate its writes cannot pass — portably, across coding-agent harnesses.

Everything in this book is running code in this repository. Every number was measured here, every mechanism has a test that fires it, and the case-history chapter reports this system's own construction bugs. Where a harness's behavior could not be verified against primary sources, the text says so instead of guessing.

Nomenclature

The book uses a fixed vocabulary. When a word below appears, it means exactly this.

TermMeaning
gateThe code that runs between an agent's proposed write and the disk, and may refuse it.
projectionThe file content a tool call would produce, reconstructed without writing it.
verdictThe gate's answer: allow, deny with a reason the model reads, or autofix — allow with rewritten input.

1 · The bottleneck

Ask one question across twenty years of tooling: where did the standard live?

First it lived in heads. The architecture was whatever the senior engineer said in review, and the wiki page nobody read was its tombstone. Then formatters and linters arrived — checkstyle, Android Lint, ktlint, detekt — and a whole class of argument died: formatting became mechanical, and format-on-save was the peace treaty. But look at what got mechanized. Whitespace. Import order. Known bug patterns. Architecture, layering, naming conventions — the things that make a codebase legible — stayed in heads and review comments. Later, tools like ArchUnit and Konsist made architecture itself assertable, which was real progress with a shared ceiling: every one of these tools judges code after it exists. Red build, failed test, review comment — all of it is reaction.

That worked because two assumptions held. Code arrived at human speed, and the author was a persistent learner — a person who absorbed the standards through review, pairing, osmosis, and stopped making the same mistake. Agents break both. A coding agent produces hundreds of lines an hour, in parallel sessions, around the clock; the review math stops closing. And an agent carries nothing between sessions. Every session is an engineer on their first day, with no onboarding, shipping to main.

The economics are worth stating precisely, because they explain why the existing tools are the right rules at the wrong time. An agent loop builds a feature for ten or twenty minutes. A pre-commit hook, a pre-push gate, or CI discovers the violation after the feature exists — and now the loop reworks finished code. The feature costs double or triple, and every rework turn burns tokens re-establishing context the first pass already had. The same violation caught at write time costs one denied tool call and one corrected retry, in the same turn, seconds apart.

Prompts do not fix this. You can write the standards into the system prompt, and the model will follow them — usually. A prompt is a suggestion to a probability distribution. Multiply "usually" by every write, every session, every day, and drift is guaranteed. The standards did not stop being right; the transmission mechanism — a persistent human author absorbing them over time — stopped existing.

So the rules have to live in the one place every change must pass: the write path itself. That is the rest of this book.

2 · The loop, and where to stand in it

Every coding-agent harness — Claude Code, Codex, Antigravity, OpenCode — runs the same loop:

 prompt ──▶ model reasons ──▶ model emits a TOOL CALL (Write / Edit / Bash)
                                        │
                                        ▼
                          ┌─────────────────────────────┐
                          │   the HARNESS executes it   │ ◀── your code can stand here
                          └─────────────────────────────┘
                                        │
                                        ▼
                          result returns ──▶ model continues

The load-bearing fact is easy to miss: the model never touches your disk. It asks the harness to. Every file your agent has ever changed went through a tool call the harness executed on its behalf — and every harness above exposes a checkpoint between the ask and the write. A hook that runs there can inspect exactly what is about to land, refuse it, and hand the model a reason it reads in the same turn.

Hooks come in four verbs, and the taxonomy is worth keeping because every harness's event list is a dialect of it:

VerbWhat it doesClaude Code name
blockRuns before a tool executes; may deny it with a reason, or rewrite its input.PreToolUse
injectAdds context at session boundaries.SessionStart
judgeDecides whether the agent is actually done, and may refuse to let it stop.Stop
auditObserves after the fact.PostToolUse

Nearly everything in this book is the first verb. The workhorse is the pre-write block: it is where enforcement stops being reactive for the first time in the history of this problem.

One dialect note that saves everyone time: Codex adopted Claude Code's hook verdict JSON — the same hookSpecificOutput.permissionDecision fields. The convergence is real and this system leans on it (chapter 6). The full per-harness matrix, including what could not be verified, is in the appendix.

3 · The gate

The gate is five small stages in stdlib Python, run once per intercepted write:

 payload ──▶ config ──▶ projection ──▶ scan ──▶ diff ──▶ verdict
             (.tenets/    (what the      (ast-grep  (only new   (allow · deny+reason
              config.toml) file WOULD     on the     findings              · autofix)
                           become)        projected   block)
                                          content)

config walks up from the file being written to the nearest .tenets/config.toml. No .tenets/ means this project never opted in: the gate is inert. projection reconstructs the post-edit content — a Write supplies it whole; an Edit is replayed against the on-disk file. scan hands the projected content to ast-grep with the enabled rules, preserving the file's real relative path so path-scoped rules (**/domain/**) can see it. diff compares finding multisets of the current and projected content, keyed by (rule, matched text) — a finding blocks only when its projected count exceeds its current count. verdict speaks the harness's JSON.

A deny is not an error message; it is the review comment, delivered early enough to be free:

{"hookSpecificOutput": {
  "hookEventName": "PreToolUse",
  "permissionDecision": "deny",
  "permissionDecisionReason": "[no-force-unwrap] line 3: Force-unwrap (!!) is banned.
   Handle nullability explicitly — use ?. with a checked fallback,
   requireNotNull(x) { \"reason\" }, or an early return."
}}

The model reads that reason and corrects in the same turn. In practice it usually does not attempt the pattern again for the rest of the session — the block message is the cheapest code review the agent will ever get, and it only has to be delivered once per session instead of once per pull request.

Equally important is what the gate deliberately does not judge. Unknown tools, file types the project does not gate, projects with no .tenets/, and edits whose outcome cannot be reconstructed (a stale old_string, a missing file) are all silent allows: the harness will reject impossible edits on its own, and the gate never double-judges. Every early return in engine/events/pretooluse.py is one of these deliberate allows, commented as such.

The canonical audit

One command defines the project's violation count: python3 .tenets/engine/audit.py . --json. It resolves configuration exactly as the hook does, scans real files at their real paths, and counts only authored rules — ast-grep's own built-in diagnostics are excluded, because scanning pack-by-pack triple-counts them (this repository learned that the honest way: a 52-versus-55 discrepancy that turned out to be the built-in unused-suppression diagnostic firing once per pack whose scan the legacy suppression didn't apply to). CI pins the number: golden must audit 0, broken must audit 52, and drift fails the build until the change is made deliberately.

4 · Rules are data

The first version of write-time enforcement everyone builds is a script per rule — and each script re-parses the language with regex, carries its own private bugs, and has no shared test harness. The failure mode is quiet: string matching cannot tell code from a string literal. A five-line hook that blocks !! also blocks "the !! operator is banned here". Strings lie. Syntax doesn't.

So rules here are data, not code: declarative YAML over a syntax tree, executed by ast-grep — one Rust engine, 25+ languages, whole-repo scans in seconds. A complete rule is small enough to read on a slide:

id: no-force-unwrap
language: kotlin
severity: error
message: Force-unwrap (!!) is banned. Handle nullability explicitly — use ?. with
  a checked fallback, requireNotNull(x) { "reason" }, or an early return.
metadata:
  tier: deny
rule:
  pattern: $A!!

Every rule ships with test cases — valid: snippets that must not match and invalid: snippets that must — and ast-grep test runs them standalone inside any pack directory. A contributor adds a rule and its tests without learning anything about the engine.

Two corpora, one discipline

Rule tests prove a pattern matches what its author imagined. Two full applications prove it behaves against reality. The golden app (twelve modules, strict MVVM+MVI, pure-JVM domain modules, single-invoke() UseCases) must audit zero — it is the false-positive corpus, and when a rule fires on it, the rule gets tightened, never the app. The broken app (two modules, ten deliberate architectural sins, fully buildable and runnable) is the positive corpus: 52 findings, each one placed. The narrowing this forces is where rule quality actually comes from — flows-over-suspend-in-repository learned to exempt one-shot mutations returning Unit because golden's toggleFavorite can't sensibly become a Flow, and that exemption is now permanent, tested knowledge.

Packs and opinions

Rules group into packs: kotlin-best-practices, android-best-practices, android-architecture (the boundary rules: no Repository in a ViewModel constructor, no android.* import in a domain module, no Context in domain, ViewModels expose state plus onAction and nothing else), and android-opinionated — where every taste split is its own rule. Prefer flows everywhere? That's a rule. Forbid UseCases composing UseCases? That's a rule too, shipped default_enabled: false because this house allows composition. Disagreement with a rule is a configuration line, not a fork, and not a reason to reject the system: install the pack, drop the rule.

5 · The invariants

These are the load-bearing laws. Each is enforced by running code and at least one test that fires it; none is aspirational.

T1 — Only new violations block. The diff compares finding multisets before and after the edit. A ten-year-old codebase with thousands of findings stays workable; finding N+1 is impossible. Enforced in engine/diff.py; proven by e2e cases 03/04.
T2 — Everything is an error. There is no warning tier. Agents ignore warnings; humans do too, honestly. A finding either blocks, is autofixed, or the rule shouldn't exist.
T3 — No side doors. The suppression comment ast-grep honors is itself a blocked pattern (no-suppression-comments). A legacy suppression keeps working one level down — and is visible one level up, where new ones cannot land. A gate with a side door isn't a gate.
T4 — Missing scanner means deny. If a project has .tenets/ and the ast-grep binary is gone, Kotlin edits are denied with an install remedy — never waved through unchecked. Proven by e2e case 07.
T5 — Not installed means inert. No .tenets/, no opinions. The gate never judges a project that didn't opt in.
T6 — Never double-judge. An edit the harness itself will reject (stale anchor, missing file) is not ours to rule on: silent allow.
T7 — Deny wins over autofix. When one edit trips both tiers, it blocks. The gate never silently fixes alongside a violation it is refusing.
T8 — Autofix never touches legacy code. For an Edit, only the incoming new_string is rewritten. Surrounding old code is never silently modernized.
T9 — One canonical number. Violation counts come from audit.py, which counts authored rules only. CI pins it.
T10 — The engine never parses rule YAML. ast-grep owns rule semantics; the engine shuttles text. Rules stay portable to any future engine.
T11 — One brain, thin shims. Exactly one gate implementation exists. Other harnesses get translators, never forks (chapter 6).
T12 — The lock preserves local edits. Every vendored file is content-hashed; update refuses to clobber files a team has modified, and doctor makes drift visible instead of mysterious.

6 · Shims and dialects

Skills are files, so the multi-agent skills ecosystem solved portability with a canonical store and symlinks. Hooks are behavior crossing a protocol — a symlink cannot translate a payload. So portability here is one brain and translators at the edges:

 Claude Code ── native ─────────────┐
 Codex ── apply_patch shim ─────────┤──▶  ONE gate engine (.tenets/engine/)
 OpenCode ── plugin (throw/mutate) ─┤        rules edited once,
 Antigravity ── pending (honest) ───┘        enforced identically everywhere

Claude Code speaks the gate's native contract. Codex sends file edits as an apply_patch envelope — a *** Begin Patch text blob — so its shim parses the envelope, projects each touched file's full content, runs each through the same gate, and merges verdicts (any deny wins, each reason line prefixed with its file). Codex's own verdict JSON is Claude-compatible, so the output side needs no translation at all. OpenCode loads a small plugin whose tool.execute.before maps the write, shells the engine, throws to deny, and mutates output.args to apply the autofix tier. Antigravity gets block-only support once its verdict schema can be pinned against a real install: its official docs page could not be machine-read at research time, and third-party accounts contradict each other on field names. That sentence is the whole policy — say what is verified, flag what is not.

The installer supports both shapes: canonical (one vendored engine, per-harness wiring pointing at it — one rule edit enforced identically everywhere) and --copy for teams that want fully independent per-harness installs (roadmap).

7 · The escalation ladder

Not every mistake deserves a conversation with a language model.

TierCostWhen
autofixsub-millisecond, zero model round-tripsMechanically fixable, judgment-free: assertEquals(true, x) becomes assertTrue(x). The hook rewrites the input in flight; the write lands clean.
deny + teachone corrected retry, same turnNeeds the model's judgment: restructure this, route it through a UseCase, name it properly. The reason says what to do instead.
humana conversationRare, and usually means a rule is wrong or a genuine design fork appeared. Rules are 15 lines; fix the rule.

The codemod tier is ordinary ast-grep fix: on the same rule file — no second system:

rule:
  pattern: assertEquals(true, $X)
fix: assertTrue($X)

One honest limitation, documented where it lives: under Codex, autofix currently degrades to a deny-with-reason, because apply_patch has no channel for handing back a revised envelope. The model fixes it itself; nothing slips through.

8 · A system that evolves

The gate is not a product you finish; it is a place your standards accumulate. The growth loop is the whole method:

When review catches something twice,
it becomes a rule with a test.
Then it stops recurring.

A rule is fifteen lines of YAML plus test cases, validated against two standing corpora — the marginal cost of making a mistake impossible is under an hour, and it is paid once. The engine side mirrors this: one orchestrator per lifecycle event dispatching to independently tested stages, so the system grows by adding a module, never by editing a monolith. The lock keeps team customization safe: vendored rules are content-hashed, local edits are never clobbered by update, and doctor reports drift with a remedy instead of a mystery.

The worked example walks the loop once, end to end, with the real artifacts — including the red run before the green one.

9 · Case history: six bugs, one bug

This system was built largely by coding agents, under exactly the review discipline it preaches. Six real defects escaped the builders' green test suites and were caught in adversarial review. They are worth a chapter because they are all the same defect:

#DefectWhy the tests were green anyway
1The scanner copied projected content to a bare temp file, erasing the real path — path-scoped rules (**/domain/**, **/test/**) could never fire on a live edit.Rule tests ran against the rules; unit tests ran against the stages. Nothing scanned a projected file at a path-scoped location through the hook.
2Three phantom findings in a sweep: ast-grep's built-in unused-suppression diagnostic, triple-counted by per-pack scanning.Both counts were "correct"; nobody had defined which command owns the number.
3The installer vendored the engine without exec bits and wired a command that needed them — every installed project had a dead gate, and doctor said "wired."The integration test asserted file layout and JSON shape. It never fired the installed hook.
4The OpenCode plugin resolved the engine relative to its own file — correct in this repo, a nonexistent path in every vendored install: all writes failed.The smoke test ran in the dev layout only.
5The Codex parser dropped bare empty lines inside hunks, making anchors unfindable — valid patches skipped, unchecked. Fail-open.No fixture contained the envelope variant reality produces.
6The runtime OpenCode plugin escaped the lock entirely — invisible to drift detection and update.Nothing asserted the lock's coverage, only its correctness for what it contained.

Every one of these is a test that admired the artifact instead of firing it in its deployed shape. Layout was checked; behavior was assumed. It is the same fake-green this whole system exists to prevent in application code, reproduced faithfully at the meta level by the tools building it — and the countermeasure is the same at both levels. Two laws came out of this history and are now house rules for the repository:

Law 1 — red before green. A gate-integrity fix lands with a regression test written first and observed failing. Defect #1's fix exists as e2e case 13, which was watched produce "expected deny, got allow" before the code changed.
Law 2 — fire the artifact. An install test runs the installed thing the way a user's harness will: the CLI's integration test now pipes a violation through the exact command it wired and asserts the deny. Green that never executed the deployed shape is not green.
