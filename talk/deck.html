The short version

Agents are about to write most of our code, and the way we enforce standards today doesn't survive that.

What does: running the rules at the moment the code gets written. It's practical, and there will be YAML.

Every rule this file breaks was written down in the repo's CLAUDE.md.
Why it happens

The agent will happily use a banned pattern.

Not because it's careless, but because it generates from probability, not from our rules. Multiply that by every session, every day, and the codebase slowly stops looking like its own architecture.
The mechanics of forgetting

Your rules are minute-one text in an hour-long context.

Attention concentrates where the model is working. The farther your CLAUDE.md drifts, the weaker its pull, and a compaction can drop it entirely.

What a lifecycle hook is

A checkpoint between
"the agent decided to write this"
and "this landed on disk."

Your script runs first, and its verdict decides whether the file changes.
Claude Code · Codex · Antigravity · OpenCode all ship these.
Build · step 1 · intercept the write
.claude/settings.json 
{ "hooks": { "PreToolUse": [
  { "matcher": "", "hooks": [
    { "command":
      "bun .tenets/engine/pretooluse.ts" }]}
]}}
what the harness hands us 
{ "tool_name": "Edit",
  "tool_input": {
    "file_path": ".../domain/Toggle…​.kt",
    "new_string": "…(context: Context)" }}
You see exactly what the model is trying to write, before it exists on disk.
Build · step 2 · project the post-edit file
packages/core/src/projection.ts 
/** The before/after content of a decidable, gated tool call. */
export interface Projection {
  path: string;
  /** On-disk content before the call ("" for a new file). */
  current: string;
  /** Content the call would produce. */
  projected: string;
}
The gate judges the projected content, never the raw edit. When the outcome is undecidable, it declines to judge rather than double-judging.
Build · step 3 · parse, don't grep
packages/core/src/scan.ts 
exec(["scan", "--inline-rules", rules, "--json=compact", tmp]);

Rules match the syntax tree, not the text.

ast-grep parses 25+ languages. A regex can't tell a Context parameter from the word Context in a comment; a syntax tree can.
Build · step 4 · one rule
packs/android-architecture/rules/no-context-in-domain.yml 
id: no-context-in-domain
language: kotlin
message: >-
  Domain code must stay platform-agnostic — drop this
  Context parameter and pass the plain data it needs.
files:  [ '**/domain/**' ]     # fires by LAYER, not file
rule:
  any: [ {kind: class_parameter}, {kind: parameter} ]
  has: { kind: user_type, regex: '^Context$' }
The files scope means this rule only exists inside domain modules.
Build · step 4 · the rule has its own tests
rule-tests/no-context-in-domain-test.yml 
valid:
  - 'fun observeListing(id: String): Flow<Listing?>'
invalid:
  - 'class FavoritesStore(context: Context)'
  - 'fun refresh(context: Context) {}'

Fifteen lines of rule, eight lines of test.

Build · step 5 · the block message is instructions
packages/core/src/events/pretooluse.ts 
function denyReason(matches: Match[]): string {
  return matches.map(m =>
    `[${m.ruleId}] line ${m.line}: ${m.message}`).join("\n");
}
Error: [no-context-in-domain] line 9: Domain code must stay platform-agnostic — drop this Context parameter and pass the plain data the domain layer actually needs.
It names the rule, the line, and the fix, and the agent applies it in the same turn.
What actually happens · real capture
⏺ Update(…/domain/ToggleFavoriteUseCase.kt)
⎿ Error: [no-context-in-domain] line 9: drop this Context parameter…
"I won't retry the identical edit or route around the hook. Two ways forward: 1. adjust the rule … 2. keep Context in the data layer so the domain stays Android-free."
The write was rejected, so the file never changed. The agent's second attempt kept Context out of the domain module.
The question half of you are asking

"Isn't this just lint?"  Mostly yes, and on purpose. Three differences matter.

What it sees
architecture and cross-file tenets, not just one file's style
When it fires
before the code exists, not minutes later in CI
Who fixes it
the generator, in the same turn, instead of a tired human
The multiplier
1×

Blocked at write time

The agent respects it the rest of the session. One correction.
2–3×

Caught at CI

It already built on top of the violation. Rewrite everything downstream.
Catch it at write time and one correction covers the whole session. Let it reach CI and the agent has already built on top of it, so everything downstream needs rewriting too.
Design decision 1 of 3 · only new violations block
19,000

legacy findings on day one

Block on those and you're uninstalled by lunch.
  • The 19,000 never block anyone
  • Finding 19,001 stops you
  • Old code migrates out safely behind the ratchet
Zero new debt lands, legacy stays workable, and it's running in production at Realtor.
Design decision 2 of 3 · there is no bypass

There is no bypass.

  • The suppression comment is itself a blocked pattern
  • If the enforcement tool is missing, edits are denied, not waved through
A gate with a side door isn't a gate, especially for an agent that will eventually find the side door. Here's the night one did.
The side door · a true story

Blocked by FP-precision rules, an agent wrote obfuscated code to a scratchpad, then wrote a mover script to smuggle it into the codebase.

$ bun demos/side-door/prove.ts
ACT 1 · Write the violation → ⛔ BLOCKED
ACT 2 · same content via mv → 🕳 UNSEEN the write gate is blind to Bash
ACT 3 · Bash counter-guard on → identical mv → ⛔ BLOCKED

We won't predict the next trick either, and that's fine.

The gate is code. When something gets past it, we add the rule that catches it. The counter-guard took an evening, and it reuses the same definition of "gated file" the write gate already uses.
Design decision 3 of 3 · everything is an error

Agents ignore warnings. (Humans do too, honestly.)

~80 ms
a blocked violation at write time, versus a full lint run, a red build, and a context switch
→ 0
lint-reason CI failures, once the same thresholds run before the code exists
The honest boundary

Rules catch the mechanical majority. They can't judge design.

No rule catches "this UseCase is conceptually wrong," and that's fine. The gate clears the convention comments out of review, and review becomes about design, which is the part humans are actually good at.

Beyond file writes

The same mechanism can watch what the agent decides.

Everything so far fired on writes. Hooks also fire on other moments in the agent's loop, and the one we care about most is the moment it decides it's finished.
The stop hook · real capture
backlog: F1 [done] · F2 [todo]
⏺ Marked F1 done. F2 remains open — stopping here.
⎿ Stop hook: You're about to stop, but 1 task is still open (1 todo):
  - F2 [todo] Add the test that proves toggling twice is a no-op
That instruction used to live in the prompt, where the model can lose track of it. Now it runs as a check every time the agent tries to stop.
Why this shape
  • Declare-then-earn: the tracker is an input you can't lie to
  • Substrate, not instruction: the nudge rides the agent's own stop. A prompt line decays at compaction; a hook fires every turn
  • Loop-safe: honors stop_hook_active, so the agent is never trapped
